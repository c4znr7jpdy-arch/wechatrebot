# 商业版远程更新发布

远程更新只发布客户二进制载荷和签名清单。自 1.0.0 起，安装包、完整载荷、在线更新包和签名稳定清单全部放在本仓库的 GitHub Release；仓库为公开仓库，Release 资产任何人可下载，安全依赖 Ed25519 签名、SHA-256 校验和激活码，不依赖地址保密。更新签名私钥只保存在发布电脑和离线备份中，不进入 GitHub、服务器或 CI。

## 首次绑定

项目已在 `config/local/update-signing-private.pem` 生成本机 Ed25519 私钥，并把对应公钥写入 `src/wechatrebot_manager/update-channel.json`。私钥已被 `.gitignore` 排除。

客户端内置的签名清单地址固定为：

`https://github.com/c4znr7jpdy-arch/wechatrebot/releases/download/stable/stable.json`

它指向固定标签 `stable` 的 Release 资产，每次发布覆盖上传，地址永远不变。Release 资产地址会 302 到 `objects.githubusercontent.com`，客户端与发布器都跟随跳转并校验最终地址为 HTTPS。

正式首发前还必须完成：

1. 把签名私钥复制到至少一份离线加密备份。私钥丢失后，已售客户端无法验证用新密钥签发的更新。
2. 不要把 GitHub 令牌或更新签名私钥放进客户程序、配置模板、日志或仓库。
3. 发布机的 `gh` 已登录且对本仓库有写权限；发布器开始前会检查。

客户安装目录可以用 `config/update-channel.json` 覆盖 `manifest_url`、检查间隔和超时，签名公钥仍固定使用程序内置值，不能被覆盖。

客户端使用仓库中已绑定的生产清单地址 `stable.json`，不是未签名的 `latest.json`。稳定清单必须先通过 Ed25519 校验，不能为了兼容示例格式而另建不带签名的版本入口。清单沿用 snake_case 字段：`version`、可选 `build`、`mandatory`、`minimum_supported_version`、`title`、`notes`，以及 `package.url/size/sha256/uncompressed_size`。`build` 与本机已安装载荷记录比较；版本或构建号不更新时不会提示。缺少非关键展示字段会回落默认标题/空更新说明；包摘要、URL、版本、签名等关键字段无效时会拒绝该更新。

开发模式不加载正式更新通道，也不会连接 GitHub。正式包可使用安装目录覆盖 `manifest_url` 指向测试用的 Release，但签名公钥固定不变，测试清单仍须由对应私钥签名。

### 0.9.9 旧通道过渡（发布时另行启用）

已安装的 0.9.9 可能仍检查 `https://ss.xiuxianjyj.xin/wechatrebot-updates/stable.json`。只把新包上传到 GitHub，不会使这些客户端自动改用新地址。当前后台部署入口不修改这个旧站点，迁移也尚未上线。

正式发布时先保存旧 nginx 配置，再在旧清单的现有处理块内，对 `User-Agent: WeChatReBot/0.9.9` 请求增加临时 HTTPS 302 跳转，目标为上面的 GitHub `stable/stable.json`。现有客户端发出的 User-Agent 已包含版本，且会跟随跳转；公钥保持 `59E10AD6E829BA64`，继续验签。旧更新包不再上传，GitHub 下载地址是唯一新产物来源。

不要把整条旧路径无条件改掉：0.9.8 及更早版本的历史渠道按项目规则保持原状。此过渡仅改变 0.9.9 的清单查询，不改变历史安装包地址；不识别 User-Agent 的请求也保持现有处理。先用真实 0.9.9 请求核对跳转、签名、包大小和 SHA-256，再验证新版从内置 GitHub 通道检查更新。失败则恢复原 nginx 配置。若不采用服务器过渡，可对指定安装的 `config/update-channel.json` 写入 GitHub 清单地址，再通过受支持更新器升级；保留其余配置字段和原公钥。

过渡配置属于另一次明确授权的线上变更，不随本次后台代码或 PR 自动部署。

## 手动发布：你需要做什么

平时改完代码并不等于用户收到更新。先把通过 CI 的改动合入 `master`，准备高于线上稳定版的版本号，再发布签名更新包。当前线上是 1.0.0，本次待发布是 **1.0.1 管理器增量**；服务器后台单独部署。

以后统一打开 `scripts/publish-github-release.ps1`，无参数运行会显示中文菜单。发布机需要 Python 3.13 x64、已登录的 GitHub CLI，以及本机原有的更新签名私钥。这些都是首次配置，不能把私钥传到 GitHub。

1. 只改管理器页面、按钮或更新逻辑：选 **1“发布管理器更新”**，填标题和说明。入口自动构建、签名、上传、核对，再让客户端看到更新。
2. 想亲自在 GitHub 网页上传：选 **2“仅生成管理器更新包”**。完成后记下屏幕显示的 `artifacts/publish-github-...` 产物目录，保留整个目录。
3. 打开 [仓库 Releases](https://github.com/c4znr7jpdy-arch/wechatrebot/releases)，点 **Draft a new release**，标签填 `v1.0.1`（以后按实际版本），Target 选对应的已合入提交，填写标题和说明。
4. 把产物目录 `update/` 内的管理器 ZIP 拖入附件区。不要改名、重新压缩或改清单；不要上传源代码目录或任何私钥。先保存草稿也可以。
5. 回到同一个 PowerShell 入口，选 **3“继续上次发布 / 验证已手动上传的文件”**，粘贴第 2 步的产物目录。它核对已有文件、补齐缺少的校验文件和签名清单、发布并公网验证，最后切换 `stable.json`。只有这一步成功，客户端才会收到更新。

上面的网页操作依据 [GitHub 官方发布说明](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)。也可以直接选 1 完成全部上传，不必到网页逐个拖文件。

### 维护者后台上传（推荐给手动操作）

如果已部署独立维护者后台，可在“发布版本”页上传本地发布入口生成的 `publish-candidate.json`、签名清单和全部更新 ZIP。后台会校验签名、源提交、quality CI，以及每个包的公网 HEAD、完整下载、大小和 SHA-256；网络中断后重新上传同一候选即可复用已存在的相同资产。上传成功不会立即通知客户，必须在页面下方使用下一组动态码再次确认“切换稳定版本”，这一步才会更新固定 `stable.json`。后台不构建、不签名，也不接受安装器或未列入清单的文件。目标 1.0.1 是管理器增量；完整载荷仍按下文流程处理。

**下载用安装包和自动更新包不是同一个文件。** 给新用户的是 `WeChatReBot-...-online-....zip`；已安装用户读取的是 `wechatrebot-...-manager-....zip` 或完整更新 ZIP，加对应签名清单。只上传安装包不会触发客户端更新。

修改 Python、依赖或原生桥接后需要完整载荷；先确认构建耗时及资源开销。本地完整包仍通过桌面 **“本地打包完整载荷”** 生成。不要把管理器增量当作完整安装包。

## 每次发布

### 管理器一键增量发布（常用）

仅修改 `src/wechatrebot_manager/`、插件中心或管理器内置 Web UI 时，先把项目版本提升到高于线上稳定版，然后执行：

```powershell
.\scripts\publish-github-release.ps1 --manager-only --title '插件配置更新' --note '修复高级配置页面'
```

该命令自动完成测试、冻结管理器、自检、生成仅含管理器 EXE 的 Ed25519 签名增量包，在 GitHub 创建 `v<版本>` Release 并上传增量包和 `.sha256`，从公网跟随跳转核对大小与 SHA-256，再把签名清单作为 `stable-<版本>.json` 存入该 Release 并覆盖到 `stable` 标签的 `stable.json`，最后按客户端逻辑做一次下载冒烟。公网核对失败时流程停止，稳定清单不更新。

> 兼容边界：`0.8.7` 之前的 PyInstaller 单文件客户端只等待应用子进程退出，没有等待仍占用管理器 EXE 的引导父进程。从这些旧版升级时必须使用完整载荷更新；线上稳定版低于 `0.8.7` 时，一键增量发布器会直接拒绝发布。完整载荷的事务预处理为旧引导进程留出退出时间，`0.8.7` 起的更新器还会显式等待两个进程并重试短暂文件占用。

后续恢复管理器增量发布前，应确认所有仍受支持的客户安装都已至少升级到 `0.8.7`；只提升线上稳定版本并不能证明离线客户已经完成过渡。

- `--dry-run`：只在本地构建和签名，不创建 Release；保留 `publish-candidate.json` 和全部产物。
- `--resume --output <原产物目录>`：恢复相同候选，已有候选不重建、不重新签名，也不要求再次读取私钥；参数仍通过同一个 PowerShell 入口传入。
- `--yes`：跳过发布前输入版本号确认，适合无人值守执行。
- `--manager-build artifacts\...`：复用已经完成且清单校验通过的管理器构建。
- `--skip-tests`、`--skip-remote-smoke`：仅用于明确知道风险的故障排查，不建议正式发布使用。

管理器增量包不会重建或遍历完整 staging，适合管理器及其内置静态资源更新。新增的 [组件增量流程](incremental-updates.md) 还支持依赖兼容的插件、桥接 Python 源码和资源变化。Python、底层依赖、AstrBot 核心补丁及 hook 等原生二进制变化仍走下面的完整载荷流程。旧客户端须先通过原有 schema 1 管理器增量升级更新器，才能接收 schema 2 组件增量；组件包绑定安装基线，不能直接向不同基线的所有客户广播。

### 完整载荷发布

Python 运行时、底层依赖、AstrBot 核心补丁、hook 等原生二进制变化必须使用完整载荷一键入口；兼容基线上的插件及桥接 Python 源码优先使用组件增量流程。该入口内部依次完成全量测试、发布元数据校验、管理器冻结、便携运行时构建、staging 组装、面向客户的在线安装 ZIP、`payload.wrb` 与在线更新 ZIP 生成、Ed25519 签名，然后创建 `v<版本>` Release、上传全部资产和 `.sha256`、从公网逐个核对、提升稳定清单并做下载冒烟；任一公网核对失败则停止，稳定清单不更新，Release 保留供排查。

```powershell
.\scripts\publish-github-release.ps1 `
  --source-root '.\vendor' `
  --title '完整载荷稳定性更新' `
  --note '修复旧版管理器更新回滚' `
  --yes
```

`--source-root` 必须指向包含桥接程序和所交付 AstrBot 插件的项目源码根目录。正式发布前项目版本必须高于线上稳定版本，签名私钥与 `gh` 登录必须可用。只需本地完整包时使用桌面“本地打包完整载荷”入口；正式发布不要跳过测试或远程冒烟。同一个版本只允许一份确定的签名候选。上传中断后保留产物目录和 Release，使用菜单 3 恢复，不必删除 Release 或重新构建。恢复时验证本地文件、签名和远端已有文件；有任何内容不一致则停止。

### 上传中断与记录

- 网络、TLS EOF、超时或 GitHub 临时错误：有限重试；失败时显示脱敏原因。关闭窗口后仍可通过菜单 3 恢复。
- `publish-candidate.json` 保存本次原始候选的提交、文件大小、摘要和上一个签名清单；不要编辑它或删除原包。
- `publication-receipt.json` 保存上传/公网校验/切换/冒烟/回滚结果。只有 `status: published` 表示这一轮完成，`smoke: skipped` 明确表示未执行下载冒烟。
- 远端已有同名文件时先下载核对，内容相同才复用；不同就停止，绝不默认覆盖。
- 切换稳定清单或下载冒烟失败时尝试恢复上一份签名清单，并记录 `rollback: verified` 或 `failed`。恢复也失败时，根据记录处理，不能声称已经恢复。
- 同时只能由一位维护者执行发布/回滚；若发现线上清单已被别的发布改动，流程会停止。

### 回滚

```powershell
.\scripts\publish-github-release.ps1 --rollback 0.9.9
```

把该版本 Release 中的 `stable-0.9.9.json` 验签后覆盖上传为 `stable` 标签的 `stable.json`，并从公网读回核对。不删除任何版本 Release。

## GitHub Release 布局

每个版本标签 `v<版本>` 上传以下资产，文件名带内容哈希前缀：

| 资产 | 用途 |
| --- | --- |
| `WeChatReBot-<版本>-Windows-x64-online-<sha12>.zip` 及 `.sha256` | 客户下载的外层 ZIP，内含 Inno 在线安装器 |
| `WeChatReBot-<版本>-payload-<sha12>.wrb` 及 `.sha256` | 在线安装器下载的完整载荷 |
| `wechatrebot-<版本>-update.zip` 及 `.sha256` | 已安装管理器的事务更新包 |
| `wechatrebot-<版本>-manager-<sha12>.zip` 及 `.sha256` | 仅管理器改动时的增量更新包 |
| `stable-<版本>.json` | 本次签名清单副本，回滚来源 |

固定标签 `stable` 只有一个资产 `stable.json`；`package.url` 指向对应版本 Release 的更新包资产地址。单个资产上限 2 GB，当前载荷约 520 MB。国内网络访问 GitHub 资产可能较慢或失败，客户端的 SHA-256 校验保证内容完整，但不能保证下载成功。

客户下载包与内部更新包用途不同：客户包是外层 ZIP，解压后包含原生 Windows 在线安装器；安装器下载并校验同一 Release 中的 `payload.wrb`。内部更新包仅供已安装管理器验证并事务更新，不能把更新 ZIP 当作客户安装包发送。资产文件名带 SHA-256 前缀，避免同版本重试时命中缓存。

发布脚本会在包内载荷清单保留 `source_manifest_status: ready` 兼容标记。该字段仅用于让 0.8.3 及更早版本通过旧版更新入口升级；新版本不再用它判断载荷是否完整或可信，仍以签名、SHA-256、路径边界和逐文件清单为准。不要手工删除该字段，否则旧版会在下载完成后拒绝更新包。这个标记只解决旧版的载荷准入，不解决上述单文件 EXE 占用问题；从 0.8.2/0.8.3 升级到 0.8.7 仍应发布完整载荷。

客户控制台会在启动约 2 秒后异步检查一次，之后按通道配置的间隔（默认 10 分钟，最小 5 分钟）检查。网络失败只影响更新提示，不影响常规启动。发现普通更新后显示新版提示。用户点击“更新”直接开始下载，不再弹下载确认；设置页显示下载和校验进度。下载校验通过后，再弹出安装确认，明确说明会强制关闭机器人程序和所有微信窗口。取消会保留已下载的包，不结束任何程序；再次选择安装时仍需确认。清单标记强制更新或当前版本低于 `minimum_supported_version` 时，会提示立即更新并阻止新的机器人启动；既有运行实例仍可安全停止。

安装会复用生命周期管理：仅在用户确认后停止并核验本安装的机器人服务，强制关闭所有 WeChat/Weixin 进程；结束进程前再次核对身份，避免 PID 复用误关其他程序。更新包再次验证和安装计划准备发生在停止程序之前，安装期间阻止新的机器人启动。被修改文件的回滚副本保留在 `updates/.rollback-<id>/`，直到新版管理器窗口发出启动确认。启动超时则恢复旧文件并启动旧管理器；系统中断更新后，下次启动会先由独立恢复副本读取更新日志、恢复文件并重新打开管理器。用户配置 `config/`（模板和安装载荷清单除外）及 `app/astrbot/data/config/` 在更新时保留；`data/`、`logs/`、`cache/`、`backups/`、`updates/` 为用户管理目录。

## 客户端安全与回滚

- 清单先验证 Ed25519 签名，再读取版本、下载地址和包摘要。
- 下载只接受 HTTPS，限制清单、压缩包、文件数量和展开体积。
- ZIP 中所有路径必须位于 `payload/`，拒绝绝对路径、路径穿越、Windows 保留名和符号链接。
- 下载完成后校验包体 SHA-256，展开后再次按 payload 清单逐文件校验。
- 当前管理器复制为独立更新程序；主窗口退出后，独立副本事务替换安装文件，因此可以安全更新管理器本身。
- 独立更新器从已验签的新载荷启动，不依赖旧客户端中可能存在的旧更新逻辑；它等待旧版 one-file 管理器与引导进程退出。
- 更新器先备份本次会改动的文件，完成替换后启动新版，并等待窗口启动确认；未确认时恢复旧文件并重新打开原管理器。
- 更新不会自动启动机器人，避免在客户未确认微信账号时直接运行。

更新日志位于安装根目录 `logs/update.log`，JSON Lines 格式，超过 2 MiB 时保留上一份 `.log.1`。用户界面仅显示错误码和处理建议，技术详情进入脱敏日志。错误码：

| 错误码 | 含义 |
|---|---|
| UPD-1001 | 获取版本信息失败 |
| UPD-1002 | 更新包下载失败 |
| UPD-1003 | 更新文件摘要或内容校验失败 |
| UPD-1004 | 磁盘空间不足 |
| UPD-1005 | 旧客户端进程未能安全退出 |
| UPD-1006 | 微信连接服务停止失败 |
| UPD-1007 | 更新文件替换失败 |
| UPD-1008 | 安装目录权限不足 |
| UPD-1009 | 新版启动未能确认，已尝试回滚 |
| UPD-1010 | 自动回滚失败，需要技术支持 |
| UPD-1011 | AstrBot 回复引擎停止失败 |
| UPD-1012 | 更新 ZIP 解压失败 |
| UPD-1013 | 更新配置或签名清单格式错误 |
| UPD-1014 | 等待微信退出超时 |
| UPD-1015 | 更新暂存目录不可写 |
| UPD-1016 | 强制更新尚未完成，禁止启动机器人 |

## 发布纪律
