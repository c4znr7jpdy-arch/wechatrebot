# 图来撤回参数修复历史记录（0.9.9）

> 2026-10-15：此文保留此前 DLL 调查和适配记录。当前撤回只调用 `POST /api/revoke_msg`——固定 DLL（微信 4.1.8.27）没有 `/api/revoke_any` 路由。当前行为见 [生图和撤回接口](image-delivery-recall-0.9.9.md)。

2026-09-24 安装日志已出现“收到图片发送回执”“绑定延迟撤回”，随后仍报 `HOOK response did not confirm completion`。此前批量回调修复已生效，本次处理回执之后的撤回请求。

## 接口差异与根因

对照 `E:\Project` 的旧实现、桥源码、API 文档本地副本以及当前固定 DLL：

- 旧实现以服务器回执中的真实消息 ID、时间和接收目标发起撤回。当前桥同样向 HTTP 接口提交这三个字段，消息 ID 转为 Python 整数，不经过浮点数。
- 文档中的 `/api/revoke_any` 要求 `newMsgId/createTime/toUserName`。当前分发的 DLL 仅注册 `/api/revoke_msg`，没有该新路由。
- 固定 DLL 的 HTTP 处理函数（RVA `0x2A10C0`）只读取 `newMsgId`，调用旧请求构造函数（RVA `0x205030`）。后者从私有缓存读取 `<ID>_createTime` 和 `<ID>_toUserName`，未使用 HTTP 请求中的同名字段。图片回执已拿到正确参数也无法保证这份缓存存在。这是本次确认的参数传递缺陷；实际微信服务端拒绝原因仍需更新后验证。
- 兼容回退另有遗漏：旧路由抛出 HTTP 404/405 时不会进入 `revoke_any`。现在只在明确不支持路由时回退；超时、普通错误或不明确的撤回结果不会重复提交。

## 实现范围

构建暂存阶段应用确定性的 DLL 适配器，直接把有效回执中的时间和目标传入原请求构造函数。原有协议编码、网络调用和成功判断保留。只提供消息 ID 的旧调用仍走缓存方式。

`release/source-manifest.json` 的 `input_sha256` 固定原始输入，`sha256` 固定转换后的输出；`release/hook-binaries.json` 与输出一致。原始输入 SHA-256 为 `21FAFB726A287093020B4CAE799C3B1839397B735BE5B8354C927052A46A6C8D`。未知输入、补丁位置不符、未知转换或输出哈希不符均阻止构建。`E:\Project` 原文件和现有安装目录不由本次修复修改。

适配器新增只读可执行 PE 节，使用相对地址以兼容 ASLR；提供新函数与原函数体跳转的 x64 异常展开信息。可审阅汇编位于 `patches/hook-recall-explicit-receipt.asm`，生成与校验逻辑位于 `src/wechatrebot_manager/hook_recall_patch.py`。

## 验证与部署边界

定向测试覆盖汇编与交付字节一致、真实机器码离线模拟、64 位消息 ID、短/长目标字符串、无效参数回退、寄存器和栈保持、PE 布局与哈希拒绝、暂存转换不修改源文件、两种接口的路由兼容及严格失败判断。并对本地固定 DLL 的副本验证确定性转换与 PE 解析，不加载 DLL，不启动微信或机器人。

真实微信撤回尚待维护者验证：群聊和私聊各发送一次“图来”，确认配置延时后图片实际消失；禁用撤回时图片保留；日志中的撤回成功应与客户端表现一致。自动化离线测试不代表微信服务端验收通过。
