# 本地增量更新

已有完整安装后，日常修改无需反复打包整套运行环境。目标版本从 `pyproject.toml` 读取。开发者入口为 `scripts/update-local-incremental.ps1`，桌面“本地增量更新”快捷方式可直接调用它。

## 日常操作

先完成代码提交、验证并合入远端 `master`，同步本地 `master` 工作树，再停止机器人；管理器也有修改时先关闭管理器窗口。双击桌面“本地增量更新”。入口自动定位当前安装，核对底层组件与安装清单，组装源码、应用项目适配补丁、检查敏感文件，生成差异包并事务安装。源码输入固定为本仓库 `vendor/`，先校验逐文件哈希，再读取 `release/source-manifest.json` 指定的条目。

只修改插件时不编译管理器；管理器源码、依赖锁或构建脚本变化时才构建管理器。首次使用时缺少管理器构建输入记录，也会构建一次管理器，以交付新的更新器。不会重建、遍历或打包 Python 与 FFmpeg。只有管理器变化时，可使用入口的 `-ManagerOnly` 选项，跳过插件组装和底层兼容检查。

`-Plan` 只做更新范围和兼容基线预检，不构建、不安装，也不提供最终字节差异统计。`-PackageOnly` 完成差异包但不安装。入口需要开发环境 Python 3.13；它不会上传、发布或启动机器人。安装后由维护者手动运行验证。

结果保存在本次 `artifacts/local-incremental-时间/`：`incremental.zip`、`update-report.json` 和必要的构建日志。成功后清理源码暂存、重复的管理器编译产物及安装临时解包文件；可复用的管理器编译环境保留。失败时保留诊断，不自动启动完整载荷构建。

## 适用范围

| 修改 | 更新方式 |
| --- | --- |
| 命令、新闻、帮助、定时任务处理代码、插件 Python/资源 | 组件增量 |
| 新增且依赖已满足的插件 | 适配并加入源码清单后，组件增量 |
| 管理器和内置界面 | 管理器增量 |
| Python、FFmpeg、依赖锁、AstrBot 核心补丁、hook DLL | 完整载荷，仍需单独确认 |

从 AstrBot 市场引入插件时，先在项目中完成平台兼容、命令/配置/定时任务适配，更新插件与源码清单并做定向验证。新增文件不局限于固定插件名单。构建器检查声明的 Python 版本和依赖是否被已安装的锁定运行时满足；新增依赖、动态依赖或无法验证的声明会拒绝。它不会运行 pip，也不能代替插件行为兼容验证或自动完成所有市场插件适配。

## 安装与回滚

差异包记录新增/修改文件的 SHA-256、受管废弃文件及其旧 SHA-256，以及安装基线指纹。安装前后均核对基线，拒绝覆盖本地改写的受管文件或同名的未登记文件。删除仅覆盖旧安装清单登记的文件；不会清空任意插件目录。用户配置、账号数据、命令配置和其他未受管数据保留，因此插件自行生成的缓存不会被猜测删除。

修改运行时代码或资源时必须停止机器人；入口只检查状态，不强制结束进程。事务备份只含本次涉及的文件、删除项和安装标记，失败恢复文件与原清单。增量安装成功后将变化合入完整安装清单，下一次继续计算差异。

## 在线更新边界

线上日常更新也使用组件差异，无需为插件或桥接 Python 修改重建完整载荷。统一打开 `scripts/publish-github-release.ps1`：菜单 1 发布组件更新，菜单 2 只生成候选，菜单 3 恢复同一候选，菜单 5 登记已发布完整 staging，菜单 6 只做兼容预检。发布机仍需现有 Python 3.13 x64、GitHub 登录和更新签名私钥。

首次登记选择已发布版本的完整 staging，例如发布结果中保存的 1.0.22 staging。入口逐项核对受管文件摘要，保存完整安装清单，但只复制组件文件、依赖锁和必要兼容元数据到 `artifacts/component-baselines/<指纹>/`；不遍历或复制 Python/FFmpeg，不默认使用开发者本机安装。缓存应随发布证据备份，不能在下一次发布前清空。

发布器默认走组件模式，完整载荷必须明确指定完整构建模式。日常流程先验证所有发布基线，复用本地增量入口的源码组装、补丁、依赖检查和发布扫描，对每个基线生成直接到目标版本的累计差异包；管理器需要变化时只构建一次。兼容检查或依赖检查失败立即停止，不自动转为完整构建。`--plan` 不构建、签名或上传；`--dry-run` 会构建并签名候选，但不上传。

新签名协议仍使用外层 schema 1，增加 `component_update_protocol: 1`，省略默认 `package`，只包含非空的 `incremental_packages`（最多 64 个不同基线）。每项含 `base_fingerprint` 和完整下载元数据；ZIP 内是现有 schema 2 载荷。目标版本、构建号、文件 SHA-256 和删除集都受原有校验约束，不能用 `--include` 截断操作集。

客户端只读 `config/installed-payload.json` 计算指纹，不扫描 Python 或 FFmpeg。精确匹配后直接选择对应包，不再要求它小于某个默认包。缺少、损坏或未知的基线会在下载前明确提示，不能回退到其他基线、显示已是最新或将旧完整包伪装成新版本。这次按维护者要求不提供旧客户端兼容过渡；组件专用清单需要包含该协议实现的新管理器，1.0.22 原管理器不能直接读取这种清单。

保留每次已发布基线可支持跳版本：例如分别生成 `1.0.22 → 最新` 和 `1.0.23 → 最新`，客户只下载其中一包，不串联补丁。发布成功后把实际安装合并结果保存为新基线，保留旧基线；独立管理器发布也更新基线缓存。超过 64 个基线时须显式选择支持范围，不能静默丢弃客户基线。

发布仍逐包执行公网 HEAD、完整下载、大小和 SHA-256 核对，再切换 stable。冒烟对每个基线重新下载、校验、解包，并只在独立临时快照中事务应用、核对目标指纹；不会改本机安装或启动机器人。冒烟每次使用独立目录，支持中断后恢复。失败沿用稳定清单回滚，成功后才登记新发布基线。候选恢复同时核对签名包、基线记录和快照指纹。

组件版本 Release 只放小包和签名清单，不更新 GitHub Latest，保留最近完整安装版本供首次安装。新增依赖、Python、FFmpeg、AstrBot 核心补丁或原生 DLL 变化仍需明确确认完整载荷。插件或桥接源码通常只有少量文件；管理器变化仍包含整个冻结 EXE，且当前构建输入判断会把版本元数据变化视为需要构建，不能保证每次只有几 MB。

更新提示、安装确认、用户数据保留和事务回滚继续沿用现有行为。代码和夹具测试不代表真实微信、实际安装升级或线上发布验收已经完成。
