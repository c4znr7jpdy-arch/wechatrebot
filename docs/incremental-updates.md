# 本地增量更新

已有完整安装后，日常修改无需反复打包整套运行环境。目标版本从 `pyproject.toml` 读取。开发者入口为 `scripts/update-local-incremental.ps1`，桌面“本地增量更新”快捷方式可直接调用它。

## 日常操作

先完成代码提交、验证并合入远端 `master`，同步本地 `master` 工作树，再停止机器人；管理器也有修改时先关闭管理器窗口。双击桌面“本地增量更新”。入口自动定位当前安装，核对底层组件与安装清单，组装源码、应用项目适配补丁、检查敏感文件，生成差异包并事务安装。源码输入固定为本仓库 `vendor/`，先校验逐文件哈希，再读取 `release/source-manifest.json` 指定的条目。

只修改插件时不编译管理器；管理器源码、依赖锁或构建脚本变化时才构建管理器。首次使用时缺少管理器构建输入记录，也会构建一次管理器，以交付新的更新器。不会重建、遍历或打包 Python 与 FFmpeg。只有管理器变化时，可使用入口的 `-ManagerOnly` 选项，跳过插件组装和底层兼容检查。

`-Plan` 只做更新范围和兼容基线预检，不构建、不安装，也不提供最终字节差异统计。`-PackageOnly` 完成差异包但不安装。入口需要开发环境 Python 3.13；它不会上传、发布或启动机器人。安装后由维护者手动运行验证。

结果保存在本次 `artifacts/local-incremental-时间/`：`incremental.zip`、`update-report.json` 和必要的构建日志。成功后清理源码暂存、重复的管理器编译产物及安装临时解包文件；可复用的管理器编译环境保留。失败时保留诊断，不自动启动完整载荷构建。

## 适用范围

| 修改 | 更新方式 |
| --- | --- |
| 命令、新闻、帮助、定时任务处理代码、插件 Python/资源 | 组件增量 |
| 新增且依赖已满足的插件 | 适配并加入源码清单后，组件增量 |
| 管理器和内置界面 | 管理器增量 |
| Python、FFmpeg、依赖锁、AstrBot 核心补丁、hook DLL | 完整载荷，仍需单独确认 |

从 AstrBot 市场引入插件时，先在项目中完成平台兼容、命令/配置/定时任务适配，更新插件与源码清单并做定向验证。新增文件不局限于固定插件名单。构建器检查声明的 Python 版本和依赖是否被已安装的锁定运行时满足；新增依赖、动态依赖或无法验证的声明会拒绝。它不会运行 pip，也不能代替插件行为兼容验证或自动完成所有市场插件适配。

## 安装与回滚

差异包记录新增/修改文件的 SHA-256、受管废弃文件及其旧 SHA-256，以及安装基线指纹。安装前后均核对基线，拒绝覆盖本地改写的受管文件或同名的未登记文件。删除仅覆盖旧安装清单登记的文件；不会清空任意插件目录。用户配置、账号数据、命令配置和其他未受管数据保留，因此插件自行生成的缓存不会被猜测删除。

修改运行时代码或资源时必须停止机器人；入口只检查状态，不强制结束进程。事务备份只含本次涉及的文件、删除项和安装标记，失败恢复文件与原清单。增量安装成功后将变化合入完整安装清单，下一次继续计算差异。

## 在线更新边界

本地 `incremental.zip` 是根目录载荷，不能直接作为在线下载包。现有 `build_update_release.py` 已支持读取它并封装成 `payload/` 结构，保留 schema 2、基线指纹与删除项，再签名；schema 2 不允许使用 `--include` 截断操作集。该能力仅负责构造更新产物，本地入口不调用它或任何发布脚本。

1.0.1 更新器支持在同一签名稳定清单中选择适合当前安装的小包。外层仍使用 schema 1，保留 `package` 作为默认包，让旧客户端继续按原规则读取。可选 `incremental_packages` 最多 64 项，每项为 `base_fingerprint` 和完整的 `package` 下载元数据；包内仍为现有 schema 2 载荷。基线重复、任一地址或摘要非法、任一包大小格式错误，都会拒绝清单。

客户端只读 `config/installed-payload.json` 计算基线指纹，不遍历 Python 或 FFmpeg。指纹精确匹配且增量包小于默认包时，只下载这个增量包；没有匹配基线或安装清单不可读取时，下载默认包。选包后将包类型、指纹和摘要一起绑定到下载身份和安装确认，下载包内的 schema、基线或内容校验失败会明确报错，不会悄悄换包安装。

`build_update_release.py` 与现有 GitHub 一键发布器支持重复传入 `--incremental-payload`，将已经生成并验证的各基线组件载荷封装成独立在线 ZIP，再把全部候选纳入同一签名。输入载荷的目标版本、构建号必须与默认包一致；默认包必须覆盖本次发布内容，不能把另一版本或未包含必要组件的包当作兜底。构建过程只读取这些组件载荷，不因此重新扫描完整运行时。GitHub 候选记录包含所有差异包，继续上传和回滚稳定清单时也逐包核对大小与 SHA-256。后台上传还需同时提供候选文件、签名清单和全部被清单引用的 ZIP，上传本身不切换稳定版本。

插件、桥接源码和资源变化可只交付几 MB；管理器增量仍包含冻结后的整个 EXE，大小取决于实际产物，不能保证每次在十几 MB 内。Python、依赖锁、AstrBot 核心补丁或原生 DLL 变化仍走经过确认的完整载荷。这里的“增量”是文件/组件差异，不是 EXE 内部的二进制差分。

客户端发现新版后先提示，点击更新即收起下载弹层，在右下角显示下载、解压、校验进度与百分比，原功能仍可操作。验证完成后再次询问是否立即安装；稍后安装会保留准备好的包。只有安装确认通过才关闭程序、覆盖文件并自动打开新版管理器；失败沿用现有事务回滚。组件更新后的安装版本从安装清单读取，避免未更换管理器 EXE 时反复提示同一组件版本。

更早的管理器须先接收兼容的管理器更新，才能使用这一选包协议。0.9.9 仍内置旧服务端清单地址，需要发布时完成通道过渡后才能发现 GitHub 的新版；相关迁移计划见 [远程更新说明](remote-updates.md)。本次代码和定向测试不代表旧客户端迁移、真实微信更新或线上部署已经完成。
