# 用户体验剩余需求审计

> 审计日期：2026-09-08  
> 范围：非技术 Windows 客户、微信群主、机器人运营者。本文只定义用户问题、优先级和验收边界，不代表功能已经完成。

## 2026-09-09 实施口径

- 长期记忆确定由 LivingMemory 单独承担；高级向量记忆只作为替代方案，禁止两套系统同时处理同一会话。
- 已进入 `0.9.0` 本地实现与测试：首次引导、按群策略、人格/情感/长期记忆设置、显式回忆与寒暄快路径、脱敏回复链路、功能准备检查、记忆与聊天记录区分、设置与记忆备份恢复、主动消息总控。
- 运行配置在线时必须走本机接口热更新并回读；离线只允许明确标记为“下次启动使用”。
- 免费 Grok 的界面与统一模型目录已经就绪，但客户独立授权、额度和停用仍依赖发行侧服务，不能用可提取的共享主密钥假装完成交付闭环。

## 实机体验待办

### UX-TODO-01 功能切换不应反复显示整页读取状态

**状态**：已实现，待安装包实机验收  
**发现日期**：2026-09-09  
**现象**：在功能中心切换左侧功能时，右侧每次都会先被清空并显示“正在读取功能设置…”。机器人尚未启动或本机控制接口响应较慢时，停留时间更明显。

**已确认根因**：前端每次选择功能都会无条件清空详情并重新调用 `get_feature`；服务端随后重新扫描功能目录、读取 Schema、功能配置和统一模型配置，并再次探测机器人在线状态。当前只有过期请求保护，没有按功能保存详情快照或复用全局在线状态。

**目标体验**：

- 第一次打开某项功能时允许显示稳定的加载状态；再次切回时立即展示本次会话中的已读取内容，不闪白、不清空表单。
- 后台以配置修订号静默检查变化；内容确有变化时再局部更新，并防止较早请求覆盖当前选择。
- 功能目录、Schema 和统一模型选项使用可失效缓存；机器人在线状态复用全局轮询结果，不因切换功能重复发起最长 5 秒的在线探测。
- “重新读取”按钮仍强制绕过缓存，保存成功后以服务端回读结果更新缓存。
- 未保存草稿不得被后台刷新覆盖；离开功能时继续使用现有丢弃修改确认。

**验收标准**：

- 已打开过的功能之间切换时，右侧内容立即可见，不再出现整页“正在读取功能设置…”。
- 首次读取、后台刷新、读取失败和离线状态均保持详情面板尺寸稳定，并给出准确的局部状态提示。
- 快速连续切换不会串页、显示旧功能内容或覆盖未保存输入。
- 机器人未启动时切换已缓存功能不触发控制接口在线探测；手动“重新读取”仍能获取磁盘上的最新配置。

**实现记录**：功能详情按功能 ID 保留本次会话快照；再次切换直接渲染缓存，不再清空右侧面板。只有首次进入、用户点击“重新读取”或保存回读时强制请求服务端，过期请求仍受序号保护。

**验收标准**：

**实现记录**：生命周期新增等待微信登录状态；系统已成功拉起微信但尚未取得登录身份时，运行中心显示正常引导和重新检测入口，不再进入红色故障态，也不会因重复点击再次拉起进程。

## 问题陈述

当前产品已经能够安装、启停、查看群聊、配置功能和模型，但用户仍需理解“模型、功能、会话标识、人格插件、记忆插件”等多个概念，才能把机器人真正放进群里稳定使用。用户需要的是从“安装完成”到“群里可用、行为可控、出错可理解”的完整闭环，而不是更多已安装模块。

## 当前判断

- 已基本闭环：两步安装、微信环境检查、一键启停、群聊静默刷新、功能用途与前置条件说明、功能配置热更新、统一模型服务、聊天记录、定时任务和签名更新框架。
- 部分闭环：群聊选择已经进入部分功能字段，但没有以“一个群”为中心统一管理机器人行为；功能卡片有静态准备说明，但不是全部功能的实时可用性检查。
- 明确缺口：当前白标 Web 控制台只有“人格称呼”，没有人格、情感、关系、记忆和回复节奏的一体化管理；备份/恢复能力存在于旧控制界面，尚未进入当前统一控制台。
- 产品冲突：商业需求当前排除 LivingMemory，但用户期待“上次说了什么”等显式记忆召回体验。应先确定唯一长期记忆口径，不能让两个长期记忆系统同时处理同一条消息。

## Must：下一阶段必须完成

### U-01 首次可用引导

**用户问题**：安装完成不等于机器人已经能在群里正常回复，用户不知道下一步还缺微信登录、模型服务、管理员身份还是群聊范围。

**验收结果**：

- 第一次打开显示一张可跳过、可再次进入的“开始使用”清单，至少检查微信、机器人账号、回复模型和目标群。
- 每一步只显示用户动作和结果，不要求理解内部组件名称。
- 未经用户明确确认，不自动启动机器人、不发送测试消息、不修改群聊配置。
- 完成后明确显示“现在可以在选定群里点名机器人测试”。

### U-02 免费 Grok 的真实交付闭环

**用户问题**：界面已经提供“免费 Grok”，但公开包不能安全携带发行方共享密钥；如果仍要求普通客户填写密钥，就没有实现开箱即用。

**验收结果**：

- 普通客户首次使用不需要看到或填写发行方主密钥。
- 单个客户的授权、额度或停用可以独立处理，不影响其他客户。
- 服务不可用、额度耗尽和网络失败分别给出可理解提示，不能统一显示成“机器人坏了”。
- 诊断、日志、预览、更新包和导出文件均不得包含可复用的发行凭据。

### U-03 以群聊为中心的管理页

**用户问题**：当前群聊页主要用于查看标识和成员，各项群配置仍散落在多个功能里；群主真正关心的是“这个群里机器人会做什么”。

**验收结果**：

- 点击一个群后能看到该群的机器人总开关、回复方式、允许功能、主动推送、安静时段和已配置任务。
- 修改群策略只进入草稿；保存时走热更新确认，不在群内发送 `/sid` 或测试消息。
- 群名变化不丢失以稳定群标识保存的配置。
- 微信接口没有返回群主或管理员身份时明确显示“未知”，涉及管理写操作时默认拒绝。

### U-04 人格、情感与记忆控制中心

**用户问题**：当前“人格称呼”只改变名称，无法管理机器人在群聊和私聊中的语气、亲密度、主动程度、称呼、表情语音与记忆方式。

**验收结果**：

- 用户能分别配置群聊和私聊的称呼、语气、回复长度、主动程度、情感表达强度和边界。
- 人格预览不向真实微信发送消息；预览必须说明是否使用记忆、表情和语音。
- “情感变化”“长期记忆”“回复节奏”分别可开关，并解释关闭后的实际影响。
- 保存后热更新；失败保留原设置，不出现一部分已生效、一部分未生效却仍提示成功的情况。
- 客户界面只出现产品概念，不要求用户理解 AngelHeart、Mnemosyne 或其他内部模块名称。

### U-05 回复速度与消息链路可解释

**用户问题**：回复变慢时，用户只能看到技术日志，不知道等待发生在回复判断、记忆、模型、表情还是语音阶段。

**验收结果**：

- 运行记录提供最近回复的白标链路：收到消息、决定回复、是否调用记忆、所用模型、是否生成表情/语音、发送完成及各阶段耗时。
- 明确点名或引用的短闲聊不额外调用“是否回复”模型；普通问候可以跳过长期记忆。
- “上次说了什么、你还记得吗、之前提到的”等显式回忆请求必须尝试长期记忆；长期记忆关闭时明确按近期上下文回答。
- 记忆检索超过预算时降级继续回复，不让一次检索无限拖住整条消息；降级结果进入运行记录。
- 技术栈名称、完整提示词、密钥和私人记忆内容不得出现在普通运行记录中。

### U-06 功能可用性而非“已安装”状态

**用户问题**：静态使用说明能告诉用户需要什么，但仍不能确认外部服务、账号绑定、模型和目标群是否真的准备好。

**验收结果**：

- 每项功能统一显示“可直接使用、还需配置、外部服务离线、当前群未启用、存在风险”之一。
- 检查动作必须只读；涉及发群消息、账号绑定或产生费用时必须另行确认。
- 依赖未满足的功能不能显示“已可用”，也不能因仅保存配置就宣称成功运行。
- 车辆提醒、游戏账号、活动网站、战绩服务、Milvus、Embedding、语音和生图等外部依赖分别给出准确下一步。

### U-07 记忆与隐私的数据控制

**用户问题**：当前“删除聊天记录副本”与“让机器人忘记”不是一回事，普通用户很容易误解。

**验收结果**：

- 界面明确区分聊天记录副本、近期上下文、长期记忆和外部账号数据。
- 用户可按个人或群聊查看数据范围，并分别执行导出、清理记录和清除长期记忆。
- 每次删除前明确说明影响范围和不可恢复内容；删除本机记录不得伪装成删除微信原记录。
- 群聊记忆默认提供知情提示和可关闭入口，不采集与功能无关的敏感信息。

## Should：重要但可排在 Must 之后

### U-08 当前控制台中的备份与恢复

- 将现有安全备份/恢复能力接入统一白标控制台，而不是只存在于旧界面。
- 恢复前验证备份、展示版本和内容范围，并自动创建恢复点；运行中不得直接覆盖配置。

### U-09 管理员与权限中心

- 从单个管理员微信号扩展为可读的管理员列表和权限范围。
- 区分机器人管理员、群管理员和普通群成员；身份无法可靠确认时采用最小权限。
- 高风险操作记录“谁、何时、对哪个群做了什么”，但不记录密钥和私人消息正文。

### U-10 主动消息总控

- 在一处汇总日报、提醒、主动聊天、成员通知和定时推送。
- 支持按群查看下一次发送时间、暂停全部主动消息、安静时段和每日上限。
- 新功能不能绕过总控直接向未授权群发送消息。

### U-11 用量、额度与降级

- 用户能看到模型服务是否可用、近期失败和大致用量状态，但不暴露发行方成本或主账号信息。
- 主回复模型不可用时明确提示是否使用备用模型；未经配置不得静默换到可能收费或风格不同的服务。

### U-12 客户可交付的诊断包

- 一键生成不含聊天正文、密钥、Cookie、完整路径和内部品牌的诊断包。
- 诊断结果先向用户列出将包含的内容，用户确认后才保存到指定位置。

## Could：验证真实使用后再决定

- 按用途提供“家庭群、兴趣群、工作群、客服群”配置模板。
- 为群主提供每周机器人使用摘要、被点名次数和失败率。
- 支持多套人格按群切换，但在单人格流程稳定前不进入首版。
- 提供移动端伴侣 App；当前没有证据证明普通群主管理必须依赖 App，不应仅为车辆提醒而强制所有用户安装。

## 明确不纳入当前范围

- 自动踢人、禁言、编辑微信群公告或绕过微信权限。
- 自动下载第三方 App、代绑车辆或游戏账号、代替用户输入验证码。
- 补拉安装前或微信离线期间未接收到的完整历史消息。
- 同时启用两个长期记忆系统处理同一会话。
- 把高风险的自动改代码能力放入普通客户默认界面。

## 实施前必须确认的三项产品决定

1. **长期记忆口径**：保留当前商业版“原生上下文 + 单一长期记忆能力”，还是恢复 LivingMemory 体验；无论选哪种，用户只看到一个“长期记忆”开关和一致的显式召回规则。
2. **免费 Grok 规则**：每位客户是否有独立额度、到期和停用策略；不能以可提取的共享主密钥作为长期交付方式。
3. **新群默认行为**：机器人进入新群后默认仅响应点名，还是完全关闭等待群主启用；在真实群主访谈前，安全默认值应为“仅响应点名且不主动推送”。

## 建议交付顺序

1. U-04 人格/情感/记忆控制中心 + U-05 回复链路与速度规则。
2. U-03 群聊中心策略页 + U-10 主动消息总控。
3. U-01 首次可用引导 + U-06 功能可用性检查。
4. U-02 免费 Grok 私有交付闭环 + U-07 数据控制。
5. U-08 至 U-12 的维护、权限、额度与售后能力。

这一路线优先解决当前已经出现的真实问题：不知道消息经过什么、回复慢、记忆是否触发、群配置分散，以及普通用户仍需理解过多技术概念。
