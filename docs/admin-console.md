# 维护者网页后台

后台地址：`https://ss.xiuxianjyj.xin/wechatrebot-admin/`。本文说明代码完成后的配置和使用步骤；代码合并不代表服务器已经部署。

## 首次启用

1. 在服务器升级完成后，通过 SSH 登录服务器，在终端运行 `wechatrebot-activation-admin admin-init`。
2. 输入两次至少 16 个字符的管理密码。终端会显示二维码；用手机验证器扫描，或输入同时显示的手输密钥。不要把终端截图发给其他人。
3. 如果需要网页切换稳定版本，再运行 `wechatrebot-activation-admin admin-set-github-token`。输入只授权 `c4znr7jpdy-arch/wechatrebot` 的细粒度 GitHub 令牌，仓库权限为 **Contents: Read and write**。GitHub 目前没有独立的“仅 Release 写入”权限，Contents 写入权限也能修改仓库内容，应选择短有效期并妥善保管。
4. 打开后台地址，输入管理密码和手机验证器的 6 位动态码。

初始化命令拒绝覆盖已有管理员。忘记密码或丢失验证器时，在服务器本机运行 `wechatrebot-activation-admin admin-reset`，重新设置密码并绑定新验证器。重置立即使原会话失效，不改动授权数据或签名私钥。

未初始化时，后台所有路径显示“未初始化”。密码、验证器密钥和 GitHub 令牌只存服务器私有目录，网页不会回显。后台不会接收授权私钥或更新签名私钥。

## 日常使用

| 页面 | 你可以做什么 |
| --- | --- |
| 概览 | 看授权、激活码、试用标识数量、最近备份时间和当前稳定版本；试用按去重标识计数，不代表独立客户人数 |
| 联系二维码 | 上传 PNG/JPEG 二维码，填写群名和截止日期；最大 512 KiB，日期按北京时间当天零点截止；保存后客户下次刷新即可看到 |
| 激活码 | 人工核实客户后，选择新开通、续期、补领或迁移；业务编号自动生成，成功后打开详情复制激活码并私下交付 |
| 发码历史 | 按客户参考号、业务编号、授权编号、码编号和兑换状态筛选记录；打开详情可查看全部发码字段、关联授权状态，并再次查看和复制新码 |
| 撤销 | 填授权编号或未兑换码编号其中一个，确认撤销；已兑换码需撤销对应授权 |
| 发布版本 | 维护更新弹窗标题和说明、保存草稿、预览后二次确认发布；高级操作保留手动上传和稳定清单回滚 |

客户参考号必须保持一致。网页上的业务编号由系统分配，无需手填；同一表单重复点击或网络重试不会再生成激活码。CLI 仍需传入唯一 `--reference`。补领、续期和迁移都需要原授权编号；迁移还需客户新设备指纹。只有已经核实换微信申请时，才勾选清除原账号绑定。

新发码加密保存激活码、客户参考号和业务编号，列表不直接显示完整码，登录后可从详情再次查看和复制。旧记录只保留既有字段，未保存的客户参考号、业务编号和激活码明文无法从摘要恢复。“已兑换”表示该码已经使用，当前授权是否仍有效需看关联授权状态和到期时间；“可兑换天数”是码的兑换期限，不是套餐使用时长。

登录会话 12 小时后失效，退出立即失效。连续 5 次密码/动态码错误锁定 15 分钟。动态码只能使用一次：刚登录后要切换版本，请等待验证器生成下一组码。

“概览”和“发布版本”先显示本地统计和操作表单，GitHub 版本信息在后台读取，不再阻塞页面切换。读取结果短时复用，点击“刷新版本信息”可重新查询；读取失败会保留已有验证结果并显示提示。刷新不会清空已选上传文件、目标版本或动态码。发布列表与稳定版本读取完成前不能切换，实际上传和切换仍重新执行实时校验。

## 如何切换版本或回滚

### 日常发布：填写说明，再二次确认

1. 请 Codex 准备待发布版本。Codex 完成构建、签名、上传及公网资产验证后，停在等待网页确认的状态，不切换稳定清单。准备入口沿用现有 GitHub 发布脚本的 `--prepare-only` 模式，支持恢复同一候选；网页不负责构建或持有更新签名私钥。
2. 打开“发布版本”，在“填写更新弹窗”中选择准备好的版本，填写标题和更新说明。标题最多 100 字，说明最多 10000 字，支持直接回车、空行、emoji 和自己的编号；按纯文本显示，不执行 HTML，也不渲染 Markdown。可点击“保存草稿”，下次进入自动恢复，保存不会通知客户端。
3. 点击“预览并发布”，在独立确认页核对当前稳定版、待发布版和说明。预览也不会切换稳定版。
4. 勾选确认通知客户端，输入新的手机验证器动态码，点击“确认一键发布线上”。后台重新核验源提交已合入 master、对应 quality CI 通过、签名候选未变、所有更新包公网大小和 SHA-256；发布说明并公网读回，再复用原稳定清单切换、读回验签和失败恢复流程。

确认仅对当前登录会话和刚预览的内容有效，10 分钟后过期，不能重复提交；预览后在其他页面修改草稿不会改变已确认的内容。源提交、候选清单或线上稳定版变化时会拒绝发布，须重新核对。操作耗时较长时等待页面结果，关闭页面不会取消已确认的后台发布事务。

更新说明是绑定“版本 + 原始签名清单 SHA-256”的独立 GitHub 资产，仅覆盖显示标题和正文，不修改签名清单、更新包、强制更新标记或其他更新规则。客户端读取失败时使用原签名说明。已有旧客户端须先升级到包含本功能的管理器，之后才能展示网页维护的说明；首次升级时仍显示候选中原签名说明。

说明公开后与该候选绑定，不能覆盖。若说明上传后后续切换失败，保留同一文案重试；需要改字时准备新候选。草稿位于服务器私有 `release-drafts/` 目录，建议随后台数据备份。

### 高级操作：手动上传更新包

需要手动接收本地产物时，展开“高级操作：手动上传更新包”。日常由 Codex 准备的版本不需要你选择这些文件。

1. 在开发机用发布入口生成候选目录，保留其中的 `publish-candidate.json`、签名清单和清单列出的全部更新 ZIP。不要改名、重新压缩或编辑文件。
2. 打开“发布版本”页面，在“上传已签名更新包”中选择这三个部分：候选记录、签名清单、全部更新 ZIP；输入当前手机验证器的新动态码后点击“上传并验证”。
3. 后台会先验证登录会话、CSRF、动态码、签名、源提交、CI 状态、每个包的大小和 SHA-256，再把资产上传到对应的 GitHub Release，并从公网做 HEAD、完整下载和摘要核对。上传中断可以重新选择同一批文件继续，已有相同资产会复用。
4. 上传成功后页面会明确显示“尚未通知客户端”。确认版本、资产和说明无误后，在下方单独输入下一组动态码，点击“确认切换稳定版本”；这一步才会更新 `stable.json`，客户端才会收到弹窗。

上传页面不会接受安装器、完整载荷或未列在签名清单中的文件。Python、依赖、AstrBot 核心补丁或 hook 变化仍须走完整载荷发布流程。仅管理器和内置 Web UI 改动可使用管理器增量。详细候选生成和本地恢复步骤见 [GitHub 发布说明](remote-updates.md)。

进入“发布版本”，选择签名通过的目标版本，输入新的动态码，点击“确认切换稳定版本”。后台会先从公网完整下载更新包并核对大小与 SHA-256，再切换 `stable/stable.json` 并从公网读回验签；大包可能需要几分钟。保留页面等待结果即可，重复点击不会绕过动态码防重放或同时切换。

选择较早版本会回滚**稳定清单**，阻止还没更新的客户获得坏版本；已升级客户端不会自动降级。需要修复已升级客户时应发布版本号更高的修复版。

切换失败会尝试恢复原清单。若网络或令牌故障导致自动恢复未完成，后台会保留 `admin-release-recovery.json`；修复后再次提交切换会先恢复。此时暂停从其他电脑发布，避免并发操作。原清单以 `stable-previous-<资产编号>.json` 保留在 stable Release，作为恢复证据。不要手工编辑签名 JSON。

GitHub 不可用或令牌被撤销时，只影响发布页面，激活码、二维码和客户授权接口继续独立工作。

## 部署和备份

服务进程使用两个独立应用，客户 API 为 8091，后台为 8092。宿主机只绑定 `127.0.0.1`，由 nginx HTTPS 转发；不要将 8092 直接暴露公网。后台响应设置 no-store、DENY 和同源 CSP；写表单必须通过会话 CSRF 校验。

开发机沿用 `scripts/deploy-activation-service.ps1` 一键入口；部署准备、支持文件同步和回滚见 [部署说明](../deploy/activation-service/README.md)。首次 nginx 配置必须包含独立的 `wechatrebot-license.conf` 和 HTTP 级 `wechatrebot-license-limits.conf`，入口通过 `nginx -T` 唯一定位，不猜主站配置。

每日备份包括 `admin-auth.json`、`admin-github.json` 和已生成的历史加密密钥 `activation-history.key`，权限为 0600。历史密钥不随管理密码或验证器重置而变化，必须与数据库成套保管和恢复；已有历史密文但密钥缺失时会停止发码和备份，需先恢复原密钥。`admin-state.sqlite3` 不备份，恢复后重新登录。备份含验证器密钥、GitHub 令牌和历史解密密钥，应与授权私钥同等级保管。所有管理操作在现有审计表中标记为 `admin-web`，不记录密码、令牌或明文激活码。

历史功能使用数据库版本 3，升级后旧服务不能打开该数据库。仅回滚旧镜像无法恢复，需恢复匹配的数据库和历史密钥并核对备份之后的业务记录，详见部署说明。本次功能仅涉及独立服务，不需要更新客户安装包。

GitHub API 权限依据：[Release assets 官方文档](https://docs.github.com/en/rest/releases/assets)。
