# 1.0.22 微信媒体接收修复候选

线上基线为 1.0.21。本次用户已明确要求合并并更新线上；PR #213 已合入 `master`（c14fb80）。本候选还包含 1.0.21 之后已合入的 #210、#212、#214，不包含仍未合入的 PR。

## 用户可见变化

- 语音和表情下载等待文件写入完成后再交付识别，避免接口先返回、文件尚未完成时被过早清理。
- 空媒体和下载未完成警告显示为「接收媒体未完成」，保留原始详情和重发建议；其他消息下载成功不会清除该条失败记录。
- 非文件类应用消息不再误走附件下载；真正的附件下载失败保留期望大小、实际大小及超时信息。
- 群聊按「明确点名才回复」规则跳过发送时作为普通记录；主动聊天使用当前日期和星期。

## 更新方式与验证边界

本次同时涉及管理器、桥接 Python 和插件源码，管理器增量不能交付完整修复。兼容基线上的组件差异可使用现有组件增量；现有在线发布器仍要求一个覆盖全部变更的完整默认包，以支持基线不匹配的客户。若使用完整载荷发布，必须先取得本次专门确认；版本准备不代表已开始构建、签名或上传。

- 媒体修复已完成红绿复现、新增 22 项测试；同步 #214 后桥接定向回归 70 项通过，管理器报告及错误目录 79 项通过。#213 两组 quality CI 均通过。
- 本候选只调整版本元数据和说明，不修改 Python、依赖锁、AstrBot 核心补丁或原生 HOOK。
- 更新清单必须使用既有 Ed25519 密钥签名；用户既有发布偏好允许管理器 Authenticode 为真实的 `NotSigned`，不得记为已签名。
- 公网 HEAD、完整下载、大小与 SHA-256、stable 清单读回验签、下载准备冒烟及失败回滚使用现有发布器，结果保存在最终 publication-receipt.json。
- 真实微信、干净 Windows、安全软件与其他既有人工验收未在本任务执行，不用 CI 替代，也不将原有 pending 状态改为 approved。
- 不更新本地安装，不启动机器人。版本准备及 CI 通过不等同于已经上线；以最终发布回执为准。
